# SSH 与远端连接排障

本参考用于 Windows 客户端通过 SSH 连接远端代理或开发环境的场景。默认只做
只读诊断，不假定 IP、用户名、端口、代理软件、安装目录或远端操作系统。

## 分层验证

按“网络路由 → SSH 握手 → 非交互认证 → 远端命令 → 代理通路 → 宿主进程”推进。
上一层未通过时，不用下一层配置掩盖问题。

先解析 SSH 别名的实际配置：

```powershell
ssh -G <host-alias>
```

关注 `hostname`、`user`、`identityfile`、`bindaddress`、转发设置、主机密钥策略
与 known-hosts 文件。不得复制私钥、公钥内容、令牌或敏感路径到输出。

用无转发、无交互的无害命令验证基础连接：

```powershell
ssh -o ClearAllForwardings=yes -o BatchMode=yes <host-alias> "printf 'ssh-ok\n'"
```

成功只证明路由、握手、主机密钥和非交互认证通过。失败时用 `ssh -vvv` 收集最小
必要片段并脱敏。

## 路由、主机密钥与认证

TCP 可达但 SSH 在认证前中断时，区分本机运行限制、路由或源地址错误、远端访问
控制和 SSH 服务故障。多网卡或 VPN 环境中先查实际出站路径；只有证据证明选错
接口时，才为单一 Host 配置 `BindAddress`。不要修改默认路由来替代诊断。

后台宿主无法回答首次主机密钥确认。确认目标身份后按 OpenSSH 正常流程维护
known-hosts，不通过关闭校验解决问题。先证明所选密钥可无提示登录，再诊断远端
命令或应用；密码提示、首次确认和交互式 MFA 都会阻断后台连接。

## 代理与反向隧道

仅当远端确实不能直接访问目标服务时才考虑代理或反向隧道。先从远端验证代理
端点，再把它用于应用。代理凭据、Cookie、设备代码和访问令牌不得写入日志、
Skill 或版本库。

应用连接 Host 只负责 SSH 与远端进程；独立隧道 Host 才配置转发。每个远端监听
端口只能有一个明确所有者。网络切换、休眠或服务器重启后，先确认监听者和进程
归属，不盲目启动重复隧道，也不终止归属不明的进程。

## 变更边界

计划任务、隧道守护、自动重连、Profile 和 wrapper 都会持久改变主机状态。只有
用户明确选择启动时机、退出行为、重连策略与清理方式后才能实施。若已审阅脚本
仅被执行策略阻止，可在用户明确触发时为单一子进程使用 `-ExecutionPolicy Bypass
-File`；不要修改系统或用户级 ExecutionPolicy。
